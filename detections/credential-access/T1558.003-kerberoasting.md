# T1558.003 — Kerberoasting

| | |
|---|---|
| **ATT&CK** | [T1558.003](https://attack.mitre.org/techniques/T1558/003/) — Credential Access |
| **Platform** | Windows (Active Directory) |
| **Data source** | Windows Security Event 4769 (Kerberos service ticket requested) |
| **Sigma rule** | [`kerberoasting_rc4.yml`](kerberoasting_rc4.yml) |
| **Status** | experimental — not yet tuned on real lab data |

## Hypothesis
An attacker with any valid domain account requests Kerberos service tickets
(TGS) for accounts that have an SPN, then cracks them offline to recover the
service account password. Tools like Rubeus request **RC4 (0x17)** encrypted
tickets because they're faster to crack. A burst of 4769 events with encryption
type `0x17` for non-machine service accounts, from a single user, is the tell.

## Simulation
Atomic Red Team **T1558.003**, or Rubeus:
`Rubeus.exe kerberoast`

## Detection logic
Match Security Event **4769** where `TicketEncryptionType == 0x17` (RC4) and the
target `ServiceName` is **not** a machine account (doesn't end in `$`). On its
own this is noisy, so alert on a *threshold* per account per hour rather than on
single events.

### KQL (Sentinel)
```kql
SecurityEvent
| where EventID == 4769
| where TicketEncryptionType == "0x17"            // RC4 — the Kerberoasting tell
| where ServiceName !endswith "$"                 // exclude machine accounts
| where TargetUserName !endswith "$"
| summarize Requests = count(), Services = make_set(ServiceName)
    by Account, IpAddress, bin(TimeGenerated, 1h)
| where Requests > 10                              // tune this threshold to your env
```

## False positives & tuning
RC4 ticket requests are legitimate in environments with older systems or apps
that don't support AES. Expect FPs from:
- Legacy applications and service accounts still negotiating RC4
- Vulnerability scanners and some backup / monitoring agents

Tuning steps:
1. Baseline normal 4769/RC4 volume per account over a week.
2. Allow-list known-legacy service accounts.
3. Raise or lower the hourly threshold to fit your baseline.
4. Better long-term: migrate those accounts to AES, then alert on *any* RC4.

_Record your before/after FP counts here once you've baselined._

## Response
1. Which account made the requests? Is it behaving normally otherwise?
2. How many distinct SPNs were targeted in the window? (Spraying = many.)
3. Check the source host for offline cracking tools / Rubeus execution.
4. If malicious: reset the targeted service account passwords (long, random),
   isolate the source host, and hunt for what the initial account accessed next.
